# @pistis/api

NestJS OAuth 2.0 authorization server, management API, and the user and
organization models behind them. Bundled with webpack; persistence is TypeORM
over better-sqlite3.

Every route sits under the global `api` prefix (`/api/users`, `/api/oauth/…`)
except the two discovery documents, which the specifications fix at the root of
the issuer origin.

```sh
cp .env.example .env
npx nx serve @pistis/api
```

## Endpoints

### OAuth 2.0

| Endpoint | Purpose |
| --- | --- |
| `GET /api/oauth/authorize` | Describes a pending authorization request for a consent screen |
| `POST /api/oauth/authorize` | Records the answer; returns the URL to redirect to |
| `POST /api/oauth/token` | `authorization_code` (with PKCE), `refresh_token`, `client_credentials` |
| `POST /api/oauth/introspect` | RFC 7662, client-authenticated |
| `POST /api/oauth/revoke` | RFC 7009, idempotent, client-authenticated |
| `GET /api/oauth/userinfo` | Bearer-authenticated; requires the `profile` scope |
| `GET /.well-known/oauth-authorization-server` | RFC 8414 metadata |
| `GET /.well-known/jwks.json` | Public signing key |

### Application and management

| Endpoint | Purpose |
| --- | --- |
| `POST /api/auth` | Sign in; returns a session token |
| `GET /api/auth/me` | The signed-in user |
| `GET/POST/PUT/DELETE /api/admin/clients` | Register, rotate secrets, delete |
| `GET/POST /api/admin/users`, `POST /api/admin/users/:id/password` | Create with a password, reset |
| `GET /api/admin/tokens`, `DELETE /api/admin/tokens/:kind/:id` | Inspect and revoke issued tokens |
| `/api/organizations`, `/api/organizations/:id/members` | Organizations and role-based membership |

The management routes require an **admin session**, which is not an OAuth access
token. Both are signed by the same key, but a session carries `typ: session+jwt`
and verification pins the type — so a client that can obtain an access token
still cannot reach the management API.

## Implementing OAuth against Pistis

This is the authorization-code flow with PKCE, which is what a web or mobile
application should use. `client_credentials` is at the end, for service-to-service
calls with no user involved.

### 1. Register a client

Clients cannot be registered anonymously. Use the dashboard
(**OAuth clients → Register a client**), or the management API with an admin
session:

```sh
TOKEN=$(curl -s -X POST http://localhost:3001/api/auth \
  -H 'Content-Type: application/json' \
  -d '{"username":"demo@example.com","password":"demo-password"}' \
  | jq -r .token)

curl -s -X POST http://localhost:3001/api/admin/clients \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{
        "clientId": "my-app",
        "name": "My App",
        "confidential": true,
        "redirectUris": ["https://my-app.example/callback"],
        "grantTypes": ["authorization_code", "refresh_token"],
        "scopes": ["profile", "email"]
      }'
```

The secret is generated by the server and **returned exactly once** — only a
bcrypt hash is stored, so it cannot be shown again. Rotate it with
`POST /api/admin/clients/my-app/secret`.

Set `confidential: false` for a client that cannot keep a secret (a SPA, a
mobile app). Public clients are issued no secret and **must** use PKCE.

Supported scopes are `profile`, `email`, `users:read` and `users:write`.
`redirectUris` are matched exactly, including the query string — register every
URI you will actually use.

### 2. Discover the endpoints

Rather than hard-coding paths, read them once at startup:

```sh
curl -s http://localhost:3001/.well-known/oauth-authorization-server
```

This returns the issuer, every endpoint, the supported scopes and grant types,
and `jwks_uri` — which is what you need in step 6.

### 3. Start an authorization request

Generate a PKCE verifier and its challenge per request, and a `state` value to
tie the callback back to the browser session that began it:

```js
const verifier = base64url(crypto.randomBytes(32));
const challenge = base64url(crypto.createHash('sha256').update(verifier).digest());
const state = base64url(crypto.randomBytes(16));
// Keep `verifier` and `state` in the user's session — never in the URL.
```

Send the browser to the **consent screen**, not to the api:

```
https://pistis.example/login
  ?response_type=code
  &client_id=my-app
  &redirect_uri=https%3A%2F%2Fmy-app.example%2Fcallback
  &scope=profile%20email
  &state=<state>
  &code_challenge=<challenge>
  &code_challenge_method=S256
```

`/login` on the web app renders the sign-in and consent UI and calls
`GET /api/oauth/authorize` to validate the request first, so a bad `client_id`
or an unregistered `redirect_uri` is refused before anyone types a password. If
you are building your own consent UI, call that endpoint yourself and then
`POST /api/oauth/authorize` with the answer.

### 4. Handle the callback

Pistis redirects to your `redirect_uri` with `code` and `state`, or with
`error=access_denied` if the person declined.

**Check `state` against what you stored before doing anything else.** A callback
whose state does not match is a cross-site request forgery, not a login.

### 5. Exchange the code for tokens

Once, and quickly — codes are single-use and expire in ten minutes:

```sh
curl -s -X POST http://localhost:3001/api/oauth/token \
  -u 'my-app:<client-secret>' \
  -d grant_type=authorization_code \
  -d code=<code> \
  -d redirect_uri=https://my-app.example/callback \
  -d code_verifier=<verifier>
```

```json
{
  "access_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6ImF0K2p3dCIs…",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "0T5s…",
  "scope": "profile email"
}
```

Public clients omit `-u` and send `client_id` in the body instead. Credentials
may go in the Authorization header or the body, but **not both** — presenting
them twice is rejected.

`redirect_uri` must be byte-identical to the one in the authorization request.

> **Replaying a code revokes everything it produced.** A reused code means it
> leaked, and the server cannot tell which party is the attacker, so the tokens
> from the first, legitimate exchange are revoked too. Exchange each code once.

### 6. Validate the access token

The access token is an RFC 9068 JWT signed with RS256. A resource server
validates it **offline** against the published key — no call to Pistis:

```js
const { keys } = await fetch(`${issuer}/.well-known/jwks.json`).then((r) => r.json());
// Cache these, keyed by `kid`, and refetch when you see an unknown one.
```

Check the signature, then `iss`, `aud`, and `exp`, then that `scope` contains
what the request needs. The claims are:

| Claim | |
| --- | --- |
| `iss` | The issuer, matching the discovery document |
| `sub` | The user; for `client_credentials`, the client itself |
| `aud` | `OAUTH_JWT_AUDIENCE`, defaulting to the issuer |
| `exp`, `iat` | Expiry and issue time, in seconds |
| `jti` | Token id — what `POST /api/oauth/introspect` and revocation key on |
| `client_id` | The client the token was issued to |
| `scope` | Space-delimited, as on the wire |

**A valid signature does not mean the token is still live.** Revocation cannot
be expressed inside a self-contained token. If your resource server must honour
revocation immediately rather than at expiry, call
`POST /api/oauth/introspect` — it is authoritative, and answers
`{"active": false}` for a revoked, expired or foreign token.

### 7. Refresh

```sh
curl -s -X POST http://localhost:3001/api/oauth/token \
  -u 'my-app:<client-secret>' \
  -d grant_type=refresh_token -d refresh_token=<refresh-token>
```

Refresh tokens are opaque and **rotate**: each refresh returns a new pair and
revokes the old one. Store the new refresh token immediately.

> Presenting a refresh token that has already been rotated revokes the entire
> family descended from that authorization code. That is the point — it is how a
> stolen token is detected — but it means a client that loses the response to a
> refresh and retries with the old token will sign the person out. Persist the
> new token before using the new access token.

You may narrow scope on refresh (`-d scope=profile`); you may not widen it.

### 8. Sign out

```sh
curl -s -X POST http://localhost:3001/api/oauth/revoke \
  -u 'my-app:<client-secret>' -d token=<access-or-refresh-token>
```

Revoking either half of a pair revokes both. Revocation is idempotent and never
reveals whether the token existed.

### Service-to-service

No user, no redirect, no refresh token:

```sh
curl -s -X POST http://localhost:3001/api/oauth/token \
  -u 'my-service:<client-secret>' \
  -d grant_type=client_credentials -d scope=users:read
```

The client must be confidential and registered for `client_credentials`. The
resulting token's `sub` is the client id, and it is rejected by `/userinfo` —
there is no user behind it.

### Common refusals

| Response | Usually means |
| --- | --- |
| `invalid_client` (401) | Wrong secret, or a public client sent one |
| `invalid_grant` on the code | Reused, expired, or `redirect_uri` differs from the authorization request |
| `invalid_grant` with `code_verifier` | The verifier does not match the challenge |
| `invalid_request` mentioning PKCE | A public client omitted `code_challenge` |
| `unauthorized_client` | The client is not registered for that grant |
| `invalid_scope` | Scope not registered to the client, or widened on refresh |

## Configuration

Read from `api/.env` by `main.ts` through Node's own `process.loadEnvFile`, so
no dotenv dependency is involved. Variables already set in the environment win,
which means `PORT=3005 npx nx serve @pistis/api` still overrides the file.

| Variable | Default | |
| --- | --- | --- |
| `PORT` | `3000` | |
| `OAUTH_ISSUER` | `http://localhost:$PORT` | Public origin; appears in tokens and metadata |
| `OAUTH_JWT_PRIVATE_KEY` | *(generated)* | PEM RSA key that signs tokens and sessions |
| `OAUTH_JWT_AUDIENCE` | the issuer | `aud` claim of access tokens |
| `OAUTH_ACCESS_TOKEN_TTL` | `3600` | Seconds |
| `OAUTH_REFRESH_TOKEN_TTL` | `2592000` | Seconds (30 days) |
| `OAUTH_AUTHORIZATION_CODE_TTL` | `600` | Seconds |
| `SESSION_TTL` | `43200` | Seconds (12 hours) |
| `OAUTH_REQUIRE_PKCE` | `false` | Require PKCE from confidential clients too |
| `OAUTH_DEV_SEED` | `false` | Create a demo admin and client at boot |
| `OAUTH_DEV_SEED_REDIRECT_URIS` | `http://localhost:3000/callback` | Comma separated |

**Set `OAUTH_JWT_PRIVATE_KEY` for anything beyond local work.** Without it a key
pair is generated at every boot, so tokens do not survive a restart and two
instances reject each other's tokens:

```sh
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out oauth-signing.pem
```

The `kid` is the RFC 7638 thumbprint of the public key, derived rather than
configured.

## Layout

```
src/
  oauth/          authorization server: grants, clients, codes, tokens, JWT
  auth/           application sessions, @CurrentUser, SessionGuard
  authorization/  CASL abilities and PoliciesGuard
  admin/          management API, behind AdminGuard
  organization/   organizations and membership/
  user/           users and password/
  common/         SchemaValidationPipe
```

Inside a feature folder: `x.ts` is the TypeORM entity, `x.mapper.ts` converts
entity↔DTO so services never leak entities, `x.service.ts` holds the repository
access and throws HTTP exceptions, `x.controller.ts` stays thin, `x.module.ts`
wires it together. `src/organization/` is the cleanest example.

## Testing

```sh
npx nx test @pistis/api
npx nx test @pistis/api -- -t "rejects algorithm confusion"
```

Specs boot a real Nest application against an in-memory SQLite database and
drive it over HTTP, so the grants, guards and policies are exercised as they run
rather than mocked.

## Notes

Persistence uses `synchronize: true` and writes `db.sqlite` to the working
directory — the workspace root under `nx serve`. There are no migrations; the
schema follows the entity decorators.

`CLAUDE.md` at the repository root explains the decisions that are not obvious
from the code, including why the database still holds a row per JWT.
